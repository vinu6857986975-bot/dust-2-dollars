Construct-AI	—	Agent	Design
Specification
This	document	defines	the	contract	(input,	output,	tools,	failure	mode)	for	every	agent
in	the	pipeline,	plus	the	orchestration	and	replanning	logic	that	ties	them	together.
1.	Orchestrator	Agent
File:
	
agents/orchestrator.py
Coordinates	all	other	agents	as	a	LangGraph	state	machine.	It	does	not	perform
domain	reasoning	itself	—	it	decides	
which	agent	runs	next
	based	on	the	current	state
and	whether	the	prior	step	succeeded.
User	Request	→	Orchestrator	→	Determine	next	agent	→	Invoke	→	Collect
	
result
			→	Check	dependencies	satisf ied?	→	Continue	or	Replan
State	object	(simplified):
Replanning	is	scoped	to	the	failing	stage	plus	any	downstream	stage	that	depends	on
it	—	never	a	full	pipeline	restart.	A	maximum	retry	count	(default	2)	prevents	infinite
loops;	on	exhaustion,	the	run	is	marked	
f ailed
	and	surfaced	to	the	user	with	the
specific	verification	error.

10.	Verification	Agent
File:
	
agents/verif ication_agent.py
This	is	the	agent	that	justifies	calling	the	system	“agentic”	rather	than	a	single
prompt-response	call.	It	checks,	in	order:
1.	
Are	quantities	within	plausible	engineering	bounds?
2.	
Are	calculations	internally	consistent	(e.g.	cement-to-sand	ratio	matches	the	mix
design	used)?
3.	
Are	all	required	materials	available	from	at	least	one	supplier?
4.	
Are	supplier	prices	within	an	expected	range	(catch	stale/bad	data)?
5.	
Does	the	delivery	plan	respect	stage	ordering	(e.g.	finishing	materials	not
delivered	before	structure)?
On	failure,	it	returns	a	structured	list	of	violations,	which	the	Orchestrator	uses	to
target	a	narrow	replan:

=== PAGE 4 ===
LLM		→		Reasoning	/	Planning		→		Tool	Call		→		Python	Calculation	Engine
		
→		Verif ied	Result
No	agent	should	return	a	number	that	didn’t	come	from	a	tool	call	into	
calculations/
,	the	database,	or	a	supplier	API.	The	LLM’s	role	throughout	is
orchestration,	classification,	and	natural-language	explanation	—	not	arithmetic.
12.	Observability
Every	agent	invocation	writes	a	row	to	
agent_logs
	(project_id,	agent_name,	action,
input_data,	output_data,	status,	timestamp).	This	powers	both	the	Agent	Execution
Log	UI	and	post-hoc	debugging	of	replans.
